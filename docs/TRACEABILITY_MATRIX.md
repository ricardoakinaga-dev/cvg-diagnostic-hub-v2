# Traceability matrix

## 1. How to read

Each row links a user problem (`P-*`) to a PRD requirement, acceptance criterion, normative specification, Build task and test strategy. The `Status` column is the normative roadmap state; the current executable evidence and limitations are summarized below and must be read together with the [AAA-3 quality bar](../.orchestrate/aaa3-execution-20260907/quality-bar.json), [executive plan](build/STATE_OF_ART_TRIPLE_AAA_EXECUTIVE_PLAN.md), [roadmap](build/STATE_OF_ART_TRIPLE_AAA_ROADMAP.md), [backlog](build/STATE_OF_ART_TRIPLE_AAA_BACKLOG.md) and the [07/09/2026 audit](RELATORIO_AUDITORIA_2026-09-07.md). AAA-2 remains a historical planning baseline.

The detailed rows retain the normative requirement-planning status used by the original specification. The current implementation state is authoritative in the coverage table above and in the AAA backlog; this keeps planned acceptance work distinct from local runtime evidence and external release approval.

The executable columns are now present. A `—` is an intentional current gap, not a pass. The matrix validator passes its structural inventory, while the complete approved SLA policy and restore acceptance still lack a complete external proof chain. NFR-OPS-001 now links a conditional local recovery-manifest chain, but it does not prove a PostgreSQL/object-storage restore drill, approved RPO/RTO or application recovery. The bounded SLA calculation fallback is linked in the backlog packet but does not satisfy the full requirement. Transfer/alta now has a policy-gated local command boundary, but D-01, UI, notification/delegation policy and target-environment evidence remain open. NFR-PERF-001/002 now link a deterministic local harness and remain `conditional local / pilot pending`; its virtual clock and synthetic dataset are evidence of reproducibility only, not the external acceptance workload. AAA2-014 adds a scoped identity contract and AAA2-030 adds queue cursor pagination; neither substitutes the relational/backfill or institutional acceptance gates. Structural traceability passing does not convert any conditional row into final acceptance.

## 5. Traceability validation rules

- Every `FR-`/`NFR-` in PRD appears in this table.
- Every `AC-` in PRD appears in a row or is explicitly marked not applicable with reason.
- Every Build task references at least one requirement and every critical requirement has a task.
- Every API command/query group in `api/API_SPEC.md` appears in `API operation traceability` with a permission/spec/task/test path.
- Every test ID appears in `testing/TEST_PLAN.md` or is a strategy family explicitly catalogued before BUILD.
- Links and exact canonical terms are checked by `scripts/validate-docs.sh`.
